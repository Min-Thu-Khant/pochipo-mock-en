## 1. 前提と資料の位置づけ

本資料は、最新のアプリ・管理画面・NACSモックを読み取り、初期リリースに向けて機能要件を整理した協議用ドラフトである。コードから確認した振る舞いと、本番実装に必要な要件案・確認事項を区別する。モックの完成を本番実装の完了とは扱わない。

- 対象は1本目のアプリと、その提供に必要な運用・連携である。2本目以降のアプリ管理は初期リリースの必須範囲には含めない。
- 今回の機能・画面・操作の基準は `Tameruko-Preview-20261013` の4189（2026-10-15確認）。旧main・過去の案と食い違う場合は現在のモックとユーザーの指定変更を優先する。
- コード、設定定義、既存テストを根拠とする。READMEとコードに差がある場合は最新コードを優先する。利用者のブラウザーに保存された個別設定は今回の調査対象に含めない。
- 実NACS、アンケート、広告SDK、ポイント管理、交換先のAPI契約・本番動作は未検証である。これらの現行仕様と検証環境は各担当から共有を受ける必要がある。
- 提供済みの方針は参照するが、本資料の優先度・達成条件・未決の数値を新たな合意事項とは扱わない。開発チームとの確認後に確定する。

## 2. 用語と開発範囲

| 用語 | 定義 |
|---|---|
| アフィリエイト案件 | 広告主サービスを利用し、指定条件の達成・承認により報酬が発生する広告案件である |
| NACS | 複数ASPからアフィリエイト案件・成果をまとめ、アプリ向けに提供する外部連携サービスである。NACS本体は今回内製しない。今回オファーウォールは前提にしない |
| 段階報酬（SUR） | 1つのアフィリエイト案件に複数の達成段階があり、段階ごとに報酬が発生する形式である |
| その他ポイント獲得機能 | 動画リワード広告、歩数、アンケート、ミニゲーム、将来のレシートキャンペーン等である |
| デイリーミッション | 動画・アンケート等への日次導線と完了表示。現モックの報酬は元の活動に属する。独立の追加報酬は設けない |
| チャレンジボーナス | 対象アフィリエイト案件の集団目標と個人の成立条件に応じて追加報酬を出す施策案である |
| 付与予定／交換可能 | 付与予定は確定前、交換可能は交換に使用できる残高である。状態の管理主体はポイント基盤と確認する |
| キャンペーンページ | 複数案件の紹介、単一案件LP、特集記事を公開するページである。報酬判定そのものではない |
| Tier | 機能の導入段階である。Tier1は初期、Tier2・3は段階的な機能拡張を表す |
| 運用Phase（既存の全体構想） | 運用方法である。Phase1は手動、Phase2はデータを見て人が運用、Phase3は判断の自動化である。Tierと同じ番号で対応するとは限らない |

初期から最低限の機能で提供を開始し、データ基盤を整備して後から改善できる方針である。手動プッシュ通知とBigQueryの初期計測・分析基盤はTier1に含める。[機能要件表](https://docs.google.com/spreadsheets/d/1g00ZxLGprVNT4T4uSmzw--vRpp95HQ1Uq9i8GnJpmS4/edit)のTier列を正とし、Tier1の要件だけをPRD本文で定義する。モックに実装されていることを理由にTierを変更しない。

モックに残るチャットのコードは初期採用を意味しない。レシートキャンペーンは既存のTier2案、自動推薦・LINE等は後続検討であり、本資料では初期の必須機能として追加しない。新規利用者のチンチロ当選率を高くする案も後の検討対象である。

### リリース優先度のPhase定義（2026-09-25・提案）

今回のPhaseは導入・リリース時期の区分。運用の成熟度（手動・分析・自動化）や既存Tierとは別軸。既存機能の割当は提案であり、将来案7件はすべて空欄とする。グループ別配信は9/25の方針でMVP対象外。F06はユーザー指定、F14は機能要件表の手動変更によりPhase1を維持する。

| 導入Phase | 意味 | 割り当てるときの判断 | 運用ルール |
| --- | --- | --- | --- |
| Phase1（初期リリース） | 最初のリリースで提供する機能・範囲。 | 初期提供に必要な体験・運用を成立させるために必要か。 | 採用する範囲と達成条件を事業・開発で確認する。具体的な機能の割当は機能要件一覧で管理。 |
| Phase2（リリース後の拡張） | 初期リリース後に追加・改善する機能・範囲。 | 初期版の利用状況・効果・開発負荷を踏まえて優先するか。 | 初期リリースの必須範囲と分けて計画する。導入日が確定したことを意味しない。 |
| Phase3（中長期の拡張） | Phase2より後の段階で取り組む機能・範囲。 | 中長期の価値と実現性を確認し、後続の計画に位置づけるか。 | 自動化・個別最適化に限定しない。将来案を自動的にPhase3へ割り当てない。 |
| 空欄（時期未定） | 採用・導入段階をまだ決めていない機能・構想。 | 候補として残すが、導入時期の判断を保留している。 | 機能要件一覧のPhaseセルは空欄のままにする。却下・対象外という意味ではない。 |
| 既存の運用Phase・Tierとの区別 | ここではリリースの導入段階を表す。 | 手動運用・データ活用・自動化という運用成熟度とは別軸。 | 番号が同じでも自動的に対応させない。 |
| 基本機能と拡張機能の区別 | 既存機能の導入Phaseを将来拡張へ引き継がない。 | 独立して採否・時期を判断する拡張は、関連IDを付けて別行で管理。 | 同じ拡張を親機能のPhase2／3欄で重ねて確定しない。将来案7件はPhase空欄。 |
| 承認状態 | Phaseは計画の区分で、仕様状態や実装完了とは別。 | 仕様状態はモック作成中／モック作成完了（チーム内合意済み）／モック確定（PO啓太さん合意済み）／廃止で管理する。 | 既存のPhase割当は引き続き提案。議事録の確認だけで全機能を承認済みにしない。 |

Phase2へ回す機能の入口・ミッション・バナーも初期リリースでは非表示にする。現在のモックは全機能を検討するための表示で、Phase1限定表示は未実装。

## 5. 連携と責任分担

基本の処理は「アプリで操作 → 自社バックエンドで要求・状態を管理 → 連携先で成立・結果を確認 → ポイント管理基盤へ依頼 → 結果をアプリに表示」である。成立・付与の履歴を別経路でBigQueryへ連携する。

| 管理対象 | 担当するシステムの案 | 確認する契約 |
|---|---|---|
| 会員・認証 | 会員・認証基盤＋自社バックエンド | 認証方式、会員ID、ゲスト、SMS、退会 |
| 掲載設定・ミッション・施策 | 自社バックエンド／運用管理画面 | 公開版、適用日時、停止、権限、変更履歴 |
| アフィリエイト案件・成果 | NACS＋接続ASP | 一覧・詳細・URL発行、成果状態、通知・照会、訂正 |
| 動画リワード広告 | 採用広告SDK・配信元＋自社バックエンド | 正式な完了通知、認証、重複、収益データ |
| アンケート | 内製アンケートシステム | 対象調査、回答画面、完了判定、報酬、計測範囲 |
| 歩数 | 端末の計測機能＋自社バックエンド | 許諾、取得元、対象日、同期、報酬判定 |
| ポイント・交換 | EDOCODE側のポイント管理基盤・交換先 | 台帳の管理元、付与依頼、確定、取消、交換、結果照会 |
| 分析 | BigQuery | 取得可能なイベント、結合ID、取り込み頻度、品質・権限 |

NACS連携の概要は、既存のデータ基盤資料の別添を参照する。この別添も現行NACS APIの定義書そのものではない。開発開始前に、API定義、認証・署名仕様、状態遷移、エラー、再送・重複・順不同・取消、検証環境をNACS担当から共有する。

## 7. 運用管理画面の範囲

管理画面の操作は、各[個別PRD](../features/README.md)の「⑤ 管理画面」を正とする。対象項目ごとに新規作成・変更・削除を分け、実際に操作できる画面と反映範囲を記載する。

- 「可能」は現在の管理画面に操作UIがあるもの。「不可」はその操作が提供されていないもの。
- 「外部管理」はNACS・EDOCODE等の担当範囲。「未実装」は現在の管理画面に専用操作UIがないもの。
- 公開停止と削除、設定モデルの存在と編集UIの完成を区別する。構想用の共通／アプリ別設定は、アプリへの実行設定の接続と分ける。
- NACS本体は内製しない。アプリ側の掲載設定、NACS側の案件・成果管理、EDOCODE側のポイント管理の境界を各PRDに記載する。

## 8. 共通の品質・セキュリティ・データ要件

以下は全機能に共通する要件案である。具体的な数値・実装方式・責任者は開発チームと確定する。

| 領域 | 要件と確認内容 |
|---|---|
| 認証・権限 | 会員は本人のデータだけを参照する。運用者は閲覧、編集、公開、配信、審査・再処理の権限を分ける。権限変更と重要操作を監査できる |
| 報酬の整合性 | 受取・成果通知・抽選・交換を識別するIDを定める。同じ要求の再送で経済的効果が重複しない。外部成功・内部未反映を照合できる |
| 通信と秘密情報 | 接続先認証・署名を検証し、秘密鍵をアプリや管理画面に埋め込まない。APIごとの入力検証と操作回数制限を設ける |
| 時刻と設定版 | 対象日のタイムゾーン、日次リセット、期間終端、予約反映、処理中の設定変更を定める。画面の端末時刻だけで報酬を判定しない |
| 性能・可用性 | 画面表示、一覧取得、受取応答、成果反映の目標時間と想定同時利用を決める。連携先障害時の縮退・再試行・復旧手順を定める |
| 画面品質 | 対象OS・端末、文字拡大、読み上げ、フォーカス、広告を閉じる操作、読込中・空・失敗・再試行、画像失敗時を確認する |
| 保存・削除 | 会員情報、成果証拠、ポイント・交換履歴、操作ログ、分析イベントごとに保存目的・期間・削除・閲覧権限を決める。180日等の仮の期限を一律採用しない |
