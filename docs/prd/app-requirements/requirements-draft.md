# 1本目のポイ活アプリ 要件定義ドラフト

2026-09-24｜v0.1｜対象アプリ：タメルコ（仮称）

## 1. 前提と資料の位置づけ

本資料は、最新のアプリ・管理画面・NACSモックを読み取り、初期リリースに向けて機能要件を整理した協議用ドラフトである。コードから確認した振る舞いと、本番実装に必要な要件案・確認事項を区別する。モックの完成を本番実装の完了とは扱わない。

- 対象は1本目のアプリと、その提供に必要な運用・連携である。2本目以降のアプリ管理は初期リリースの必須範囲には含めない。
- GitHub `ca-toju/pochipo` の `main` を取得し、コミット `91eb741ffa285f1baeb88a7733ea8a8442ae7e02` を基準とした。読取時のローカル作業ツリーに未コミット変更はなかった。
- コード、設定定義、既存テストを根拠とする。READMEとコードに差がある場合は最新コードを優先する。利用者のブラウザーに保存された個別設定は今回の調査対象に含めない。
- 実NACS、アンケート、広告SDK、ポイント管理、交換先のAPI契約・本番動作は未検証である。これらの現行仕様と検証環境は各担当から共有を受ける必要がある。
- 提供済みの方針は参照するが、本資料の優先度・受入基準・未決の数値を新たな合意事項とは扱わない。開発チームとの確認後に確定する。

| 表記 | 意味 |
|---|---|
| モック確認済み | コード上の挙動である。本番採用・安全性・API互換を保証するものではない |
| 方針 | これまで共有された開発の方向性である。技術方式・詳細条件は別途確認する |
| 案・候補 | 本資料で提示する要件、初期範囲、受入条件である |
| 要確認 | 関係者間で決定、または実連携で検証する必要がある事項である |

## 2. 用語と開発範囲

| 用語 | 定義 |
|---|---|
| アフィリエイト案件 | 広告主サービスを利用し、指定条件の達成・承認により報酬が発生する広告案件である |
| NACS | 複数ASPからアフィリエイト案件・成果をまとめ、アプリ向けに提供する社内サービスである。今回オファーウォールは前提にしない |
| 段階報酬（SUR） | 1つのアフィリエイト案件に複数の達成段階があり、段階ごとに報酬が発生する形式である |
| その他ポイント獲得機能 | 動画リワード広告、歩数、アンケート、ミニゲーム、将来のレシートキャンペーン等である |
| デイリーミッション | 指定行動の達成に対して追加の報酬を受け取る機能である。対象機能自体の報酬と区別する |
| チャレンジボーナス | 対象アフィリエイト案件の集団目標と個人の成立条件に応じて追加報酬を出す施策案である |
| 付与予定／交換可能 | 付与予定は確定前、交換可能は交換に使用できる残高である。状態の管理主体はポイント基盤と確認する |
| キャンペーンページ | 複数案件の紹介、単一案件LP、特集記事を公開するページである。報酬判定そのものではない |
| Tier | 機能の導入段階である。Tier1は初期、Tier2・3は段階的な機能拡張を表す |
| Phase | 運用方法である。Phase1は手動、Phase2はデータを見て人が運用、Phase3は判断の自動化である。Tierと同じ番号で対応するとは限らない |

初期から最低限の機能で提供を開始し、データ基盤を整備して後から改善できる方針である。手動プッシュ通知とBigQueryの初期計測・分析基盤はTier1に含める。各ポイント獲得機能の採否は、価値・費用・連携条件を確認して決める。

モックに残るチャットのコードは初期採用を意味しない。レシートキャンペーンは既存のTier2案、自動推薦・LINE等は後続検討であり、本資料では初期の必須機能として追加しない。新規利用者のチンチロ当選率を高くする案も後の検討対象である。

## 3. 現在のモックと本番化の境界

| 領域 | コードで確認した状態 | 本番化に必要なこと |
|---|---|---|
| アプリ画面 | 下部4タブ、上部メニュー、獲得機能、案件・特集を表示する | ネイティブアプリでの再実装、実状態・APIとの接続 |
| 保存 | アプリと旧運用画面はブラウザー内の状態を共有する | サーバー保存、会員ごとの分離、権限、監査、バックアップ |
| NACS | 案件・順位・成果・再通知をローカルに再現する | 現行API、チャネル、認証、通知・照会・再処理の契約 |
| 動画・アンケート・歩数 | タイマー、サンプル設問、手動歩数で操作を再現する | SDK・内製API・端末データとの接続と成立確認 |
| ポイント | ローカルの付与予定・確定・履歴を操作する | GMOメディア側との付与・審査・照合・取消の分担 |
| 交換・招待・認証 | 説明画面またはデモ状態変更が中心である | 申請・会員登録・招待成立等の実処理 |
| プッシュ | アプリ内お知らせはあるが端末への実配信はない | 手動配信、宛先・許諾・抑止・結果確認 |
| 共通／アプリ別設定 | 構想用の保存先で設定を保存・コピーする | 実アプリへの適用経路。現コードは反映未接続と明示する |

特に、アフィリエイト参加操作だけで成果を作ること、ブラウザー内の乱数で報酬を決めること、ローカルの審査ボタンで一括確定することはデモ用の処理である。本番の成立・付与を保証する仕組みではない。

## 5. 連携と責任分担

基本の処理は「アプリで操作 → 自社バックエンドで要求・状態を管理 → 連携先で成立・結果を確認 → ポイント管理基盤へ依頼 → 結果をアプリに表示」である。成立・付与の履歴を別経路でBigQueryへ連携する。

| 管理対象 | 担当するシステムの案 | 確認する契約 |
|---|---|---|
| 会員・認証 | 会員・認証基盤＋自社バックエンド | 認証方式、会員ID、ゲスト、SMS、退会 |
| 掲載設定・ミッション・施策 | 自社バックエンド／運用管理画面 | 公開版、適用日時、停止、権限、変更履歴 |
| アフィリエイト案件・成果 | NACS＋接続ASP | 一覧・詳細・URL発行、成果状態、通知・照会、訂正 |
| 動画リワード広告 | 採用広告SDK・配信元＋自社バックエンド | 正式な完了通知、認証、重複、収益データ |
| アンケート | 内製アンケートシステム | 対象調査、回答画面、完了判定、報酬、計測範囲 |
| 歩数 | 端末の計測機能＋自社バックエンド | 許諾、取得元、対象日、同期、報酬判定 |
| ポイント・交換 | GMOメディア側のポイント管理基盤・交換先 | 台帳の管理元、付与依頼、確定、取消、交換、結果照会 |
| 分析 | BigQuery | 取得可能なイベント、結合ID、取り込み頻度、品質・権限 |

NACS連携の概要は、既存のデータ基盤資料の別添を参照する。この別添も現行NACS APIの定義書そのものではない。開発開始前に、API定義、認証・署名仕様、状態遷移、エラー、再送・重複・順不同・取消、検証環境をNACS担当から共有する。

### F01 会員登録・認証・利用者情報

現状：デモ切替のみ。初期範囲：初期必須案。

| 観点 | 要件・現状・確認事項 |
|---|---|
| 目的・評価指標 | 利用者とポイントの帰属を一意に管理する。登録完了率、認証失敗率、アカウントに関する問い合わせを確認する。 |
| 対象範囲・優先度 | 初期リリースに必要な基盤である。ゲスト利用・ゲストからの引き継ぎは採用要否を決める。複数アプリ間の会員統合は今回の対象に含めない。 |
| 対象・利用条件 | 会員・未登録・認証期限切れ・利用停止・退会済みを区別する。年齢条件とSMS認証を要求する操作を決める。認証方式は未確定である。 |
| 画面・操作・状態 | モックは利用者の状態を切り替えて登録完了を再現する。実際の登録、ログイン、再認証、ログアウト、退会、端末変更時の復旧画面は別途必要である。 |
| 成立・報酬ルール | 会員登録だけでポイントを付与する要件は確定していない。プロフィール登録報酬もモック上の提案である。ゲスト残高を引き継ぐ場合は移管の成立条件を定める。 |
| 連携・責任分担 | 会員・認証基盤が本人の識別を担い、自社バックエンドが接続先の利用者IDとの対応を管理する構成案である。モックのAmeba表記は新アプリの認証方式の決定を意味しない。 |
| 運用・変更・終了 | 会員の検索、停止・復帰、認証状況の確認、退会処理の権限を定める。運用者がパスワードや秘密鍵を閲覧できる構成にはしない。 |
| 例外・不正対策 | 複数端末、重複登録、アカウント乗っ取り、通信切断、引き継ぎの重複を扱う。認証期限切れでポイント履歴が別会員へ結び付かないことを条件とする。 |
| データ・計測・問い合わせ | 利用者ID、接続先IDの参照、登録日時、認証状態、同意の版と日時、停止・退会状態を管理する。分析用には仮名IDを用い、電話番号等を無条件にBigQueryへ複製しない。 |
| 受入基準（案） | 別会員の残高・履歴を参照できない。再ログイン後も同じ履歴に到達できる。退会後の新規付与・配信の扱いが決定したルールどおりになる。 |

### F03 アフィリエイト案件の一覧・検索・カテゴリ・並び順

現状：ローカルのNACS連動モックあり。初期範囲：初期候補。

| 観点 | 要件・現状・確認事項 |
|---|---|
| 目的・評価指標 | 利用できるアフィリエイト案件を発見できるようにする。詳細閲覧率、参加操作率、承認成果率を別々に確認する。 |
| 対象範囲・優先度 | 一覧・検索・カテゴリを初期候補とする。個人別の自動推薦は初期要件に含めない。ガポガポ・すぐできるの名称と選別条件は確認事項である。 |
| 対象・利用条件 | 配信状態、期間、対応OS、利用者条件で対象を選ぶ。モックの「金融利用済みなら金融全除外」「動画回数によるインストール案件解禁」は本番採用を確認する。 |
| 画面・操作・状態 | お得内におすすめ／ガポガポ／すぐできる／マイ案件がある。おすすめで検索・カテゴリ・すべてを選べる。取得中・0件・取得失敗の表示と再読込導線を用意する。 |
| 成立・報酬ルール | 表示・検索・詳細閲覧は成果成立ではない。報酬は定額、定率、段階報酬を区別し、NACSから受け取る金額・率の意味を確定する。 |
| 連携・責任分担 | NACSが案件・一覧コード・掲出順を管理する。アプリは受け取った順を利用する案である。検索がサーバー検索か取得済み範囲内か、ページングと件数をAPIで確認する。 |
| 運用・変更・終了 | モックはピン留めを先頭、残りを当日を含む3暦日JSTのクリック数順、同数は候補順、計20件までとする。対象外除外後に上限を適用する。TOPの関連カテゴリも同じ順序を参照する。これは本番採用前の具体案である。 |
| 例外・不正対策 | ピン留めでも配信停止・非対応の案件を表示対象に戻さない。検索途中の通信失敗、0件、期限切れ、並びの更新で同じ案件が重複表示される場合を扱う。 |

## 7. 運用管理画面の初期範囲

1本目を運用できることを優先する。複数アプリへの一括適用・設定コピー・個別例外管理を、初期の全機能に必須とはしない。将来拡張のため、設定や記録がどのアプリに属するかは識別できる設計とする。

| 運用領域 | 初期に必要な操作の案 | 本番化で確認する点 |
|---|---|---|
| TOPメニュー | 名称・順番・表示内容・アイコンの編集 | 適用日時、初期対象外機能の選択制限 |
| デイリーミッション | 文言・報酬・有効状態・案件閲覧ミッション・リンク | 開始後の変更、日次上限、権限 |
| チャレンジボーナス | 掲載順・アイコンの編集、NACSへの導線 | 条件の管理元、成立確定、既存参加者の精算 |
| バナー＆テキスト広告 | 枠選択、画像・テキスト・リンク・期間・公開状態 | 規定寸法、配信0件、POPUP競合、公開前確認 |
| キャンペーンページ | 採用する形式のページ編集・公開・終了 | 下書き、承認、更新版、画像・CTAの検証 |
| ミニゲーム | 採用ゲームの回数・報酬・確率・停止 | サーバー判定との接続、変更の適用単位 |
| 歩数・動画・アンケート | 報酬・上限・還元率と適用時期 | 連携元との整合、年齢・許諾条件 |
| 手動プッシュ | テスト、対象確認、送信、未送信分停止、結果確認 | 配信権限、回数上限、静穏時間、宛先管理 |
| 照会・復旧 | 成果・付与・交換の状態照会、許可された再処理 | 再処理の権限と監査、外部結果との照合 |

共通値は現在の構想では「コピー元となるひな形」であり、変更しただけで全アプリに自動反映するものではない。この意味を、設定画面と実際の保存・公開処理で一致させる必要がある。単一アプリの初期運用でも、編集・保存・公開・反映済みの状態を区別する。

新たなミニゲームやレシート機能の追加は、設定項目の追加だけで完結しない。アプリ画面、成立判定、連携、報酬、管理画面、計測を開発・確認し、対応するアプリ版を公開してから運用で有効化する。既に対応している記事ブロックや掲載内容の変更は、管理画面から運用できる範囲とする。

## 8. 共通の品質・セキュリティ・データ要件

| 監視・復旧 | 通知未処理、付与失敗、交換結果不明、設定配信失敗、データ欠損を検知する。バックアップと復旧を試験する |
| 配布・変更 | 旧アプリ版で未対応の機能を有効にしない。設定の取り消し・公開停止、障害時の切り戻しを定める。テスト用残高・案件を本番に混入させない |

分析の詳細は既存の「データ基盤・パーソナライズ要件整理」を参照する。本資料は各機能の成立・運用・受入を補うものであり、分析仕様を別の定義で置き換えるものではない。
