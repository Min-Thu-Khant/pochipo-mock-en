1. 前提と資料の位置づけ

本資料は、最新のアプリ・管理画面・NACSモックを読み取り、初期リリースに向けて機能要件を整理した協議用ドラフトである。コードから確認した振る舞いと、本番実装に必要な要件案・確認事項を区別する。モックの完成を本番実装の完了とは扱わない。

  • 対象は1本目のアプリと、その提供に必要な運用・連携である。2本目以降のアプリ管理は初期リリースの必須範囲には含めない。
  • GitHub ca-toju/pochipo の main を取得し、コミット 91eb741ffa285f1baeb88a7733ea8a8442ae7e02 を基準とした。初回調査時のローカル作業ツリーに未コミット変更はなかった。v0.2以降は第12節に記載した追補を含む。
  • コード、設定定義、既存テストを根拠とする。READMEとコードに差がある場合は最新コードを優先する。利用者のブラウザーに保存された個別設定は今回の調査対象に含めない。
  • 実NACS、アンケート、広告SDK、ポイント管理、交換先のAPI契約・本番動作は未検証である。これらの現行仕様と検証環境は各担当から共有を受ける必要がある。
  • 提供済みの方針は参照するが、本資料の優先度・達成条件・未決の数値を新たな合意事項とは扱わない。開発チームとの確認後に確定する。

リリース優先度のPhase定義（2026-09-25・提案）

今回のPhaseは導入・リリース時期の区分。運用の成熟度（手動・分析・自動化）や既存Tierとは別軸。既存機能の割当は提案であり、将来案7件はすべて空欄とする。グループ別配信は9/25の方針でMVP対象外。F06はユーザー指定、F14は機能要件表の手動変更によりPhase1を維持する。

Phase2（リリース後の拡張） 初期リリース後に追加・改善する機能・範囲。 初期版の利用状況・効果・開発負荷を踏まえて優先するか。 初期リリースの必須範囲と分けて計画する。導入日が確定したことを意味しない。
Phase3（中長期の拡張） Phase2より後の段階で取り組む機能・範囲。 中長期の価値と実現性を確認し、後続の計画に位置づけるか。 自動化・個別最適化に限定しない。将来案を自動的にPhase3へ割り当てない。
空欄（時期未定） 採用・導入段階をまだ決めていない機能・構想。 候補として残すが、導入時期の判断を保留している。 機能要件一覧のPhaseセルは空欄のままにする。却下・対象外という意味ではない。
既存の運用Phase・Tierとの区別 ここではリリースの導入段階を表す。 手動運用・データ活用・自動化という運用成熟度とは別軸。 番号が同じでも自動的に対応させない。
基本機能と拡張機能の区別 既存機能の導入Phaseを将来拡張へ引き継がない。 独立して採否・時期を判断する拡張は、関連IDを付けて別行で管理。 同じ拡張を親機能のPhase2／3欄で重ねて確定しない。将来案7件はPhase空欄。
承認状態 Phaseは計画の区分で、仕様状態や実装完了とは別。 仕様状態はモック作成中／モック作成完了（チーム内合意済み）／モック確定（PO啓太さん合意済み）／廃止で管理する。 既存のPhase割当は引き続き提案。議事録の確認だけで全機能を承認済みにしない。

Phase2へ回す機能の入口・ミッション・バナーも初期リリースでは非表示にする。現在のモックは全機能を検討するための表示で、Phase1限定表示は未実装。

5. 連携と責任分担

基本の処理は「アプリで操作 → 自社バックエンドで要求・状態を管理 → 連携先で成立・結果を確認 → ポイント管理基盤へ依頼 → 結果をアプリに表示」である。成立・付与の履歴を別経路でBigQueryへ連携する。

管理対象 担当するシステムの案 確認する契約
会員・認証 会員・認証基盤＋自社バックエンド 認証方式、会員ID、ゲスト、SMS、退会
掲載設定・ミッション・施策 自社バックエンド／運用管理画面 公開版、適用日時、停止、権限、変更履歴
アフィリエイト案件・成果 NACS＋接続ASP 一覧・詳細・URL発行、成果状態、通知・照会、訂正
動画リワード広告 採用広告SDK・配信元＋自社バックエンド 正式な完了通知、認証、重複、収益データ
アンケート 内製アンケートシステム 対象調査、回答画面、完了判定、報酬、計測範囲
歩数 端末の計測機能＋自社バックエンド 許諾、取得元、対象日、同期、報酬判定
ポイント・交換 GMOメディア側のポイント管理基盤・交換先 台帳の管理元、付与依頼、確定、取消、交換、結果照会
分析 BigQuery 取得可能なイベント、結合ID、取り込み頻度、品質・権限

NACS連携の概要は、既存のデータ基盤資料の別添を参照する。この別添も現行NACS APIの定義書そのものではない。開発開始前に、API定義、認証・署名仕様、状態遷移、エラー、再送・重複・順不同・取消、検証環境をNACS担当から共有する。

7. 運用管理画面の範囲（採用Phaseに連動）

共通値は現在の構想では「コピー元となるひな形」であり、変更しただけで全アプリに自動反映するものではない。この意味を、設定画面と実際の保存・公開処理で一致させる必要がある。単一アプリの初期運用でも、編集・保存・公開・反映済みの状態を区別する。

新たなミニゲームやレシート機能の追加は、設定項目の追加だけで完結しない。アプリ画面、成立判定、連携、報酬、管理画面、計測を開発・確認し、対応するアプリ版を公開してから運用で有効化する。既に対応している記事ブロックや掲載内容の変更は、管理画面から運用できる範囲とする。
