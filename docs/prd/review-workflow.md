# メンバーでPRDをレビューしてmainへ反映する手順

PRDレビュー中は、レビュー済みのモックを維持する。**担当PRDだけを作業ブランチで変更し、青木が最新mainとの差分を確認してから、1件ずつmainへ取り込む。**

mainはチームの共有版、作業ブランチは個人の編集場所、プルリクエスト（PR）は変更内容を確認して取り込むための申請を指す。

## 全員が守る5つのルール

1. **1機能につき担当者1人・ブランチ1本・PR1件。** 同じPRDを同時に編集しない。着手前に機能ID・担当者・PRリンクをチームで共有する。同じ機能の次の修正は、先のPRを取り込んでから始める。
2. **毎回、GitHubの最新mainから新しいブランチを作る。** 昨日のローカルファイルや終了済みのブランチを再利用しない。古い保存ファイルを丸ごと貼り戻さない。
3. **編集するのは担当の `docs/prd/features/Fxx-*.md` だけ。** 本文・達成条件・未決事項・変更履歴を同じファイル内で更新する。モック、画像、プログラム、設定は変更しない。共通方針・一覧・機能要件表への波及はPRに書き、青木が別の変更として調整する。
4. **mainに直接アップロードしない。** 作業ブランチをGitHubへ上げ、main宛てのPRを作る。取り込みは青木が担当する。強制プッシュ、履歴の巻き戻し、競合時の片側一括採用はしない。
5. **mainへ取り込む直前に、最新mainを作業ブランチへ取り込んで再確認する。** 競合（同じ箇所の変更がぶつかること）が出たら作業を止め、青木に相談する。前の担当者の変更を消して解決しない。

## 進め方

| 順番 | 担当 | やること・完了条件 |
| --- | --- | --- |
| 1. 着手 | メンバー | 担当と対象ファイルを確認。未保存・未コミットの作業があれば保全してから、最新 `origin/main` を取得し、新規ブランチを作る。開始時のコミットをPRに残す。 |
| 2. レビュー | メンバー | 書かれた内容を正しく理解する。不明な意図はAIに質問し、解消しない疑問はPRDの未決事項へ残す。利用者の操作・結果、条件・ポイント、例外・運用を確認する。技術的な実現可否の判断は今回の対象外とする。 |
| 3. PR作成 | メンバー | 担当ファイルだけをコミット・プッシュ。PRに「機能ID／変更理由／変更点／疑問・他機能への影響／確認結果」を書き、青木へ確認を依頼する。 |
| 4. 最終確認・取り込み | 青木 | 最新mainを作業ブランチへ取り込み、下の4点を確認してからマージする。複数PRは1件ずつ処理し、次のPRは更新されたmainで再確認する。 |
| 5. 完了 | 青木・メンバー | GitHubのmainで変更が読めることを確認し、完了したPRのリンクを共有する。次の作業は、更新後のmainから別ブランチで始める。 |

「PRの取り込み完了」は「仕様の最終確定」とは別。レビュー・PO合意の記録なしに、版・仕様状態・Tierを変更しない。

## 青木がマージ前に確認する4点

- **変更ファイル：** PRの「Files changed」が担当PRDだけになっている。モックや設定、他担当のPRD、個人の試作が混ざっていない。
- **既存内容の維持：** 最新mainとの差分を読み、すでに取り込まれた修正・決定事項・未決事項を意図せず消していない。他機能との矛盾があれば解決するか、担当・未決事項を残す。
- **検証：** `npm run docs:check`・`npm run check`・`npm test` が通っている。検証後にmainやPRを変更した場合は、更新後の状態で再確認する。
- **モックとの差分：** PRDだけで新しく決めた内容は「モック未反映」として記録されている。PRDを合わせるために、依頼されていないモック修正を混ぜない。

古いブランチでも、Gitの通常のマージは変更していないファイルを丸ごと古い版へ戻す処理ではない。ただし、古い内容での上書きや誤った競合解消では他人の修正を失う。競合が出なくても、文章の意味が矛盾することはあるため、最新mainとの差分確認は省略しない。

## AIに作業を頼むときの文面

`F08`とファイル名、担当者名は自分の担当に置き換える。

```text
F08のPRDレビューを行います。
担当者：〇〇
編集対象：docs/prd/features/F08-walking.md

docs/prd/review-workflow.mdを読んで進めてください。
既存の未コミット変更を削除・上書きせず、混ざる場合は別worktreeで作業してください。
origin/mainをfetchして、そこから docs/prd-f08-review-担当者-日付 という
新しいブランチを作成してください。開始時のコミットを記録してください。

これから伝えるレビュー結果を、対象PRDの本文・達成条件・未決事項・変更履歴に反映してください。
モック・画像・コード・設定・他のPRDは変更しないでください。
共通資料や機能要件表への影響は、変更せずPRの確認事項に書いてください。
合意のない仕様確定、Tier変更、疑問点の推測による確定はしないでください。

完了後は最新origin/mainを作業ブランチへmergeしてください。
競合が出たら片側を一括採用せず、青木への相談内容を示して止めてください。
最新mainとの差分で、担当ファイルだけが変更されていること、既存の変更を消していないことを確認し、
npm run docs:check、npm run check、npm testを実行してください。
担当ファイルだけを明示してコミット・プッシュし、main宛てのPRを作成してURLを教えてください。
mainへの直接プッシュ・PRのマージ・force pushはしないでください。
```

## GitHubで追加するとよい防止策（この文書の追加では設定しない）

作業ルールに加え、mainの保護ルールで「PR必須」「承認必須」「承認後に差分が変わったら再承認」「強制プッシュ禁止」を設定する。青木の承認を必須にする場合は、担当PRDのコードオーナー指定とその承認必須設定など、担当者を限定する仕組みも必要。

自動チェックを追加する場合は、PRDレビュー用PRの変更が指定PRD内に収まるかの検査と資料・既存テストの検証を用意する。そのチェックを必須にし、「最新mainへの追従必須」も有効にする。管理者の迂回権限を含め、実際の適用範囲を確認する。

現時点のローカル確認では、PRテンプレートはあるがGitHub Actionsのチェック定義はない。GitHub側の保護設定は未確認であり、この手順が自動で強制される状態とは扱わない。

設定の詳細は[GitHub公式：保護されたブランチ](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、更新操作は[PRをベースブランチと同期する](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/keeping-your-pull-request-in-sync-with-the-base-branch)を参照する。
