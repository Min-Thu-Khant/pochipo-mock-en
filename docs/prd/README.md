# 機能別PRD

1機能を1ファイルで管理します。独立して優先度を決められ、完成条件を確認できる単位を機能とします。アプリと管理画面が一体の機能なら同じPRDに両方を記載します。

## 作り方

1. [採番ルール](../features/README.md)に沿って未使用のIDを割り当てる。
2. [規定FMT](../templates/feature-prd.md)をこのフォルダへコピーし、`PCH-F-0001-daily-mission.md`のように命名する。この名前は形式の例であり、まだ採番していない。
3. 全体構想・既存モック・根拠の議事録を読み、確定値と【仮】・【未決】を区別して記入する。
4. 変更時は本文と完成条件を更新し、変更履歴に理由・根拠・確認者を残す。

IDは機能名や優先度が変わっても固定します。廃止したPRDは削除せず、状態を「廃止」にして後継IDを記載します。部品ID（P-01等）とは別の識別子です。

## 状態は分けて記録する

- 仕様状態：草案／確認中／確定／廃止
- モック状態：未反映／一部反映／反映済み／対象外
- 開発会社の実装状況：受託先の管理方法が決まってから紐付ける。モック完成を本番実装完了としない。

「確定」は責任者の確認を受けた範囲だけに使います。議事録の提案やモックの見本値だけでは確定しません。

## 現在の収録状況

[1本目のアプリの機能要件定義ドラフト](app-requirements/README.md)を収録しています。18機能（F01〜F18）の本文・閲覧用HTML・根拠ファイル・検証記録は、最新mainの内容を一式保持しています。記録内のコミットと検証結果は作成時点のものです。

このドラフトは確定PRDではありません。既存IDのF01〜F18は維持します。個別PRDへ分割する際は元の機能との対応を明記し、PCH-F形式との重複採番を避けます。[全体構想](../product/README.md)や[過去の仕様案](../archive/README.md)も、機械的に確定仕様へ変換しません。
